# 素材上架：怎麼把影格交到播放器手上

播放器要的是一組網址加上幾個設定值。它們從哪裡來，本專案刻意不管——但「不在範圍內」
不等於「不重要」。產生那些網址的東西，正是一個捲動序列從 demo 變成「一個團隊真的能
營運的功能」的分界線。

這一頁講的就是那個東西怎麼設計。**與平台無關**：不管你用低程式碼建站平台、自己架的
伺服器，或是決定根本不需要後台，都適用。

---

## 後台只需要做四件事

**1. 把 N 張圖變成 N 個網址。**
批次上傳，依檔名排序。要用**自然排序**不是字串排序——`f_2.webp` 必須排在
`f_10.webp` 前面，而字串比大小會排錯。做法是把數字拆出來當數字比。

**2. 把那份清單存起來，而且要存得住。**
比聽起來難。見下一節。

**3. 接住那些設定值。**
停留點、拼接圖格線、手機跟拍時間表。全部都是純資料，做成表單就好。

**4. 讓操作者確認順序沒錯。**
這件事一行字就解決了八成。見後面。

---

## 清單怎麼存

### ⚠️ 不要把清單塞進單一文字欄位

150 個網址，每個約 100 字元，大約 20 KB。加上頁面其他內容之後就會超過欄位長度上限，
**寫入失敗**。

失敗本身還算好查。真正危險的是「先寫本機快取再寫資料庫」的儲存流程：

```
① 寫 localStorage   ← 一定成功
② 寫資料庫           ← 失敗了，而錯誤被吃掉
```

| 誰 | 看到什麼 |
|---|---|
| 站長（有快取） | ✅ 150 幀都在，預覽完全正常 |
| 每一個訪客 | ❌ 什麼都沒有 |

**沒有人會發現**，因為檢查的人永遠是有快取的那一個。

### 分塊存

把網址清單獨立成自己的一種紀錄，而且切塊：

| 欄位 | 說明 |
|---|---|
| `sequence_id` | 這是哪一組序列——見後面第二個坑 |
| `chunk_index` | 第幾塊，0、1、2… |
| `urls` | 這一塊的網址，JSON 陣列字串 |
| `total_frames` | 整個序列總共幾幀 |

**每 25 個網址一筆**很好用：150 幀變成 6 筆，每筆約 2.5 KB。小到離任何欄位上限都很遠，
少到「抓整組序列」是一次查詢而不是 150 次。

### 在瀏覽器端快取

把組好的網址清單同時寫進 `localStorage`——大約 20 KB，設一週左右過期。

第二次進站時這份清單是**同步**就拿得到的，所以首屏畫的已經是逐幀本身，而不是一張
封面在等資料庫回應。同時在背景重新抓一次、更新快取，這表示換了影格之後，回訪的訪客
最晚下一次進站就會看到。

| | 動畫能開始之前要讀幾次資料庫 |
|---|---|
| 一個網址一筆 | 150 |
| 分塊 | 6 |
| **分塊 + 快取，回訪** | **0** |

最後那一列才是重點。**一個要等網路的 Hero 動畫，等於沒有人看得到它的開頭。**

## 操作者必須能改的設定

以下全部都是播放器本來就吃的資料。後台的價值在於讓人不碰程式碼就能改——
以及**擋住那些改了會壞掉的值**。

### 停留點

| 欄位 | 是什麼 | 陷阱 |
|---|---|---|
| `index` | 釘在第幾幀 | 播放器是 0 起算；如果介面是 1 起算，轉換只能寫在一個地方 |
| `weight` | 這個停留點額外佔多少捲動距離 | 見下 |
| `weightMobile` | 手機版的同一件事 | **必須另外設**，見下 |
| `mode` | `loop` 或 `pingpong` | `make_loop.py` 會告訴你，不要用猜的 |
| `fps` | 循環的播放速率 | **必須對應素材怎麼抽的**，見下 |
| `frames` | 循環的影格網址 | |
| `framesMobile` | 手機用的低解析度版，選填 | 留空就沿用 `frames` |
| `intro` | 選填，一次性開場，只在第一次進入時播 | 結束在定格姿勢的動作不是循環 |

**第一格的 `weight` 應該設 1。** 那是待機動畫：使用者停在頂端時無限播，一往下捲就
立刻離開。設更大就變成他們得先「捲過」它，頁面才開始動。

**手機的 weight 不是同一個數字。** 手機跑的是抽樣後的序列——48 張而不是 150 張——
所以同樣一單位的捲動涵蓋了三倍的劇情。直接沿用桌機的值，會讓一個停留點變成要捲
兩個半螢幕。**大約取桌機的三分之一**是個好起點。

**`fps` 必須對應素材怎麼抽的。** 24 張撐 4 秒是 6fps；48 張撐同樣 4 秒是 12fps。
設錯就會變快轉或慢動作，而且不會有任何線索告訴你為什麼。

### 拼接圖格線

| 欄位 | |
|---|---|
| `sheetUrl` | 拼接圖 |
| `sheetCols` / `sheetRows` | 格線 |

`build_spritesheet.py` 會把兩個數字都印出來。**必須跟產生時完全一致**——錯一個數字，
整段動畫每一格都會顯示錯的格子。建議把它們跟拼接圖網址存在一起，而不是讓人手動重打。

### 手機跟拍

一份 JSON 時間表（見
[`schema/mobile-pan.schema.json`](../schema/mobile-pan.schema.json)），
加上 `mobileFrameCount`——手機要抽樣成幾張。

**建議做成整份 JSON 貼上的欄位，不要做關鍵影格編輯器。** 那份時間表是看著素材寫出來的，
本來就發生在後台之外；一個能對 schema 驗證的文字框，比一個限制你能表達什麼的表單有用。

## 最省時間的那一個畫面

上傳完顯示這一行：

```
共 150 幀，150 個不重複編號
```

兩個數字必須一樣。不一樣就代表有重複或缺號，而操作者是在**發布前**知道，不是發布後。

另外三件值得做的，按「能省下多少痛苦」排序：

**重傳前先清空。** 沒清空就傳新的一組，會變成 `f_001舊 / f_001新 / f_002舊 …` 交錯，
總數翻倍。順便提供「保留每組最後上傳的」修復按鈕——穩定排序會讓相同編號維持上傳
順序，所以這功能只有幾行。

**在面板標題顯示這是哪一組序列。** 如果一個上傳器服務多個頁面，而序列識別碼寫死了，
在第二個頁面上傳會無聲覆蓋掉第一個，而第二個頁面自己還讀不到。識別碼要當參數傳進去，
**而且要顯示出來**：標題上「開場逐幀 — *首頁*」這幾個字，能讓錯誤在發生前就被看見。

**永遠不要讓寫入失敗默默過去。** 尤其當站長自己的畫面是從快取來的。
一個會擋住發布的紅框，價值高過任何預覽功能的打磨。

## 三條實作路徑

### A. 根本不做後台

如果只有工程師會更新序列，你不需要後台。把 `frames/` 整個資料夾放上靜態託管，
旁邊產一份 `manifest.json` 記錄網址清單和設定值，播放器讀它就好。

最省的做法，沒有資料庫可以壞，而且跟網站其他部分一起進版控。
**除非有非工程師要改，否則從這裡開始。**

### B. 低程式碼建站平台

只要平台有「檔案上傳」和「自訂資料表」就做得起來。把上面說的分塊紀錄做成資料表，
再在上面疊一個上傳面板。

這頁的兩個坑在這條路上咬得最兇，因為平台的欄位長度限制很少寫在顯眼的地方，
而寫入失敗可能根本不會浮出來。

### C. 自有伺服器

一個上傳端點把檔案寫進物件儲存、回傳網址；一張資料表存清單；一個管理頁。
多花的力氣在權限和上傳進度，核心邏輯跟 A 一模一樣。

---

不管選哪條，播放器要的東西都沒變：**一組網址、幾個設定值。**
這正是把這一塊留在函式庫之外的原因——**怎麼存是關於你的團隊的決定，
不該由一個動畫元件替你決定。**
