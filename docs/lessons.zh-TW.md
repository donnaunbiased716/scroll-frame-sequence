# 經驗教訓

哪裡壞掉、量到了什麼，以及哪些事不值得再試一次。之所以跟操作說明分開放，是因為
這部分通常沒有人會寫下來。

## 三個不會噴出錯誤訊息的 bug

### 在 `<html>` 上設 `overflow-x: hidden`

```css
html, body { overflow-x: hidden; }   /* ✗ */
body { overflow-x: clip; }           /* ✓ */
```

在 `<html>` 上設 `overflow-x: hidden` 會讓它變成捲動容器，於是 `position: sticky`
**對整頁的每一個後代元素都失效**。沒有錯誤，沒有警告。影格序列就是不會動，而第一
直覺一定是序列的程式碼壞了。

`clip` 會裁掉同樣的溢出，但不會建立捲動容器。

### <a id="storage"></a>把影格 URL 塞在單一 CMS 欄位

150 個 URL、每個約 100 字元，大約是 20 KB。再加上頁面其餘的內容，就超出欄位上限，
資料庫寫入失敗。

光是這樣還找得出來。真正危險的是儲存路徑：

```
1. 寫入 localStorage   ← 一定成功
2. 寫入資料庫          ← 失敗
```

而這個失敗被 `.catch(console.error)` 吞掉了。結果是：

| 誰 | 看到什麼 |
|---|---|
| 有 `localStorage` 的編輯者 | 全部 150 張影格，預覽正確 |
| 每一位訪客 | 什麼都沒有 |

**沒有人會發現**，因為負責檢查的那個人手上永遠有快取。

兩個修法，兩個都值得做：把影格 URL 存進自己的記錄並分塊（每列 25 個 URL，各約
2.5 KB）；以及當編輯者自己看到的畫面是由一個會遮蔽問題的快取供應時，絕不讓寫入
失敗變成靜默失敗。

### 兩個序列共用一把寫死的 key

同一個上傳工具服務兩個頁面，但儲存 key 被寫死成 `'home'`。在第二個頁面上傳會覆蓋
掉第一個頁面的影格，而第二個頁面還是讀不到自己的。

把 key 當參數傳進去，並且**顯示在 UI 上**。面板標題寫著「開場序列 — *home*」，能
讓錯誤在發生之前就被看見，而不是發生之後。

## 估錯的數字

把這些記下來，是因為錯的數字比對的數字更有用：它告訴你你的直覺往哪邊偏。

| 估計 | 實際 | 原因 |
|---|---|---|
| WebP 比 JPEG 省 60–70% | **53%** | 那個被引用的數字假設基準是高品質 JPEG；我們的素材本來就壓過了 |
| 拼接圖會落在 800 KB – 1.5 MB | **2.0–2.9 MB** | 高頻素材、150 張各不相同的影格，沒有東西可以去重 |
| 降低品質就能解決檔案大小 | **並不會** | q75 → q55 只省 20%，卻換來看得出來的畫質損失；從 12.4 MB 起算，五組設定之間只差 1.2 MB |
| 降噪能省下位元組 | **7%** | 那不是雜訊，那是細節 |
| 放大過的和原生的檔案大小差不多 | **原生大 55%** | 放大過的影格比較平滑，所以壓得比較好——這裡的「比較小」代表資訊比較少 |

規律是：**素材一旦夠細緻，壓縮設定就是很弱的槓桿。**強的槓桿是影格數量和解析度，
而這兩者都會改變你的格線數字，所以要早點決定。

## 生成素材

### 循環不會閉合，就算你開口要求也一樣

標準建議是把同一張靜態圖同時餵成第一格和最後一格，好讓模型回到起始姿勢。在一批
片段上實測，影格 0 對上最後一格，以正常單步變化量的倍數表示：

| 片段 | 比值 |
|---|---|
| A —— 緊特寫、小動作 | 4.2x |
| B —— 廣角、多個主體 | 6.3x |
| C —— 同構圖、動作更少 | 7.7x |
| D —— 平坦背景、低對比 | 2.3x |

完美的循環會接近 1.0。**假設片段不會閉合，然後挑一個不需要它閉合的播放模式**——
來回播放不用付出任何代價，而且在結構上就消掉了接點。

不同的生成器在這裡表現不同。先量你自己那一套，再照結果設計。

### 想靠剪掉一段來救壞掉的循環，通常會失敗

有個片段在循環中段燈光掉了下去，把暗的那一段剪掉之後，接點反而*更糟*：19.2，原始
版本是 9.6，而正常單步是 4.5。剪掉一段，也就順手剪掉了讓兩端相似的那些影格。

### 開場不是循環

一次性的動作、結束在一個定住的姿勢——某個東西升到定位然後停住——沒辦法循環。第一
格和最後一格照設計本來就不一樣，硬要循環就會讓那個動作像波浪一樣反覆倒放。把它拆
成一段一次性的開場加上一段循環，而且使用者往回捲時不要重播開場。

## 判斷題，不是 bug

值得寫下來，因為它們一直回來，而且沒有正確答案。

**9:16 的畫面容不下分處兩端的兩個主體。**這是幾何，不是演算法。要嘛加黑邊、接受
所有東西都變小；要嘛選一邊、放棄另一邊。唯一錯誤的做法是默默決定。

**動態加權抽樣平均而言比較好，而且需要阻尼。**純比例加權會刪掉刻意安排的安靜段落
——而停住的那一刻往往*正是*重點。`w = 0.35 + 0.65·m/mean` 會在安靜的部分留下幾張
影格。

**影格更多不等於更好。**每格低於約 10 px 之後，你是在為沒有人能在捲動速度下察覺的
細節付錢。

**來回播放會把動作倒著放。**呼吸、布料、閃爍的光——沒有代價。落下的程式碼、飄動的
煙、單向的風——看得出來，這時誠實的答案是交叉溶接或重新生成。沒有任何量測能可靠地
決定這件事；自己看片段。

## 審查紀律

抓到最多問題的習慣，依價值排序：

1. **出貨前先做一張編號的樣張表。**「第 61 格不對」可以行動；「中間某個地方看起來
   怪怪的」不行。
2. **用實際顯示尺寸比較，不要放大看。**在最終頁面上只佔 130 px 的一張臉，不需要撐
   得住 300% 的像素級檢視；照像素級檢視來判斷，會讓你花上好幾個小時處理沒有人看得
   到的差異。
3. **量接點，不要用眼睛猜。**兩張影格之間的平均絕對差，以正常單步的倍數表示，一個
   數字就告訴你這個切點會不會被看見。
4. **把估錯的數字報出來。**上面每一個錯的數字，都來自事前先把估計寫下來。少了這一
   步，結果就只是一個數字，什麼也學不到。
